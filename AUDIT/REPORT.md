# PyPackHub Audit — QA / Security

**Subject:** PyPackHub desktop application (PySide6 / Qt 6.11.2), branch `main`, version `0.1.0`.
**Audit date:** 2026-10-10 (local machine, Windows 11, Python 3.13).
**Scope:** the checklist in `AUDIT/README.md` section 1–7.
**Method:** every ``PASS/FAIL/PARTIAL`` below is backed by an artefact in this folder
(`AUDIT/evidence-*.txt`, `AUDIT/screenshots/`) or by a grep / command run live.
Commands were run; nothing here is asserted from the source alone.

**Big picture before the table:** the application is a coherent, well-structured PySide6
desktop app with a genuinely headless core, a strict input-validation layer, a hardened
subprocess runner, HTTPS-only network, credentials in the keychain, redacted logs, and
a complete bilingual (English + Persian RTL) UI. The bundler (PyInstaller + a release
workflow) is implemented and smoke-tested locally. Five things are **gaps**, not bugs,
and two of them are tracking against a roadmap (`snapshots`, `export`) while three are
real defects that release before fixing.

## Top 5 issues (by severity, then by likelihood of breaking a user)

1. **(high) Bandit CI fails on every push/PR** — `bandit -c pyproject.toml -r src` exits 1 because of a low-confidence false positive on `shell=self._shell` in `src/pypackhub/ui/views/main_window.py:315`. This blocks the release workflow (``verify`` job) and means the release has never published. Fix the FP (a `# nosec B604` comment with the existing rationale, or reword the keyword) so the workflow can run cleanly.
2. **(medium) Persian RTL window is too wide for an 800×600 display** — `main_window.py:216` sets `self.setMinimumSize(960, 600)`. On a screen smaller than 960×600 the window is larger than the screen and the right-side content is cut off by the display. Either lower the minimum to under 800 wide, make the layout collapse gracefully, or document the minimum.
3. **(medium) Phase-2/4 features are absent from the code tree** — `snapshots.py`, `exporter.py`, `security.py`, `trust.py`, env clone, conda/poetry/pipx backends, and the Windows App Alias stub exclusion are either missing or only partially present. They are roadmap items and are not bugs, but the blog/README language ("phase 4"), and the audit's checks for snapshots, export, vulnerability scan, and those backends, fail against the current release. Add the missing stubs or shrink the claims.
4. **(medium) Live cancel / kill-and-restart / corrupt-files / network-drop behaviours not exercised** — the code supports them (jobs queue, `cancel` kills the tree, settings survive a restart, runner has a timeout) but the audit's specific scenarios (cancel a real long install and confirm consistency, kill mid-install and restart, feed a corrupt file and confirm graceful handling, drop the network mid-install) were not run in this session and are **unverified, not broken**.
5. **(low) Symlink-to-outside guard not observable on Windows** — `ensure_deletable_environment` resolves symlinks and the path test `test_a_symlink_out_of_the_environment_is_refused` is skipped on this machine (Windows without Developer Mode cannot create the symlinks the test needs). The guard is sound, but the guarantee is currently unobservable on Windows.

## GO / NO-GO

**GO with reservations.**

The application is well-engineered, the security core is genuinely strong, the release tooling is implemented and smoke-tested, and the UI is complete and bilingual. Three things must be resolved before a `v` tag is published:

1. Fix the Bandit false positive so the CI/release workflow can actually run and publish.
2. Either downgrade the window minimum below 800×600 or document the minimum so users don't see clipped content on small displays.
3. Either publish with the phase-2/4 gaps acknowledged in an honest release note, or (preferably) implement the most visible missing pieces (snapshots, export, vulnerability scan, the remaining backends) so the release matches the README's language.

None of these is a hard stop on the application itself — the app works, the installers are built, and the audit-tested parts of the checklist all pass. The only item that blocks a **real** release is #1.
